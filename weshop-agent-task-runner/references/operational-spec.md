# WeShop 本地表单服务与 CLI 执行器

## 最终目标

交付并启动一个仅供本机使用的 Web 表单服务。用户在浏览器中填写 Agent/模型所需的参数，服务端始终通过官方来源可获得的最新版 WeShop CLI 同步执行任务，并在同一次请求中将最终媒体结果返回页面。

此 Skill 的完成标准不是生成请求 JSON、项目源码或“复制命令”按钮，而是：服务进程已在用户本机运行、本地地址可以访问、页面可以点击提交、实际调用 WeShop CLI，并展示经过核验的最终结果。只交付文件但未启动服务，视为未完成。

```text
浏览器表单
    ↓ HTTP（仅本机）
本地表单服务
    ↓ 子进程，WESHOP_API_KEY 环境变量注入
最新版 WeShop CLI（同步等待结果）
    ↓
最终任务状态、媒体 URL 或错误
    ↓
本地表单服务返回并展示
```

## 服务边界

- 服务默认仅监听回环地址（`127.0.0.1` 或 `localhost`），不得默认暴露到局域网或公网。
- 浏览器绝不持有、显示、传输或保存 API Key。服务进程从环境变量 `WESHOP_API_KEY` 读取凭证，并在启动时检查其存在。
- 服务不得把 API Key、认证头、Cookie 或签名写入日志、HTML、JavaScript、请求预览、任务记录或结果对象。
- 表单提交必须由服务端执行 CLI；浏览器端不能直接执行 shell 命令。
- 不得用静态请求预览替代提交能力。若 CLI、Agent Schema 或本地服务不可用，页面须显示明确的不可执行原因，且禁用提交。

## 本地运行前置条件

| 配置 | 必需 | 说明 |
| --- | --- | --- |
| `WESHOP_API_KEY` | 是 | 仅由本地服务进程通过环境变量读取。 |
| `WESHOP_CLI_COMMAND` | 是 | WeShop CLI 可执行命令。 |
| `WESHOP_LOCAL_SERVICE_URL` | 仅 CLI 支持本地服务时需要 | 受信任本机服务地址，例如 `http://127.0.0.1:<port>`。 |
| `HOST` / `PORT`            | 否                        | 本地表单服务监听地址；默认仅回环地址和一个可用端口。 |

启动或处理首个请求前：

1. 每次启动服务及每次执行任务前，检查 CLI 是否存在、当前版本和官方安装源可获得的最新版本。
2. 检查当前weshop CLI版本，若 CLI 缺失或当前版本不是最新版本，必须从官方来源安装/升级到最新版（npm i weshop-cli）；随后重新确认安装后的版本和帮助输出。不得沿用旧版 CLI、根据旧版帮助生成表单，或因为升级失败而静默降级执行。
3. 验证 `WESHOP_API_KEY` 已由环境注入，但绝不输出其值。
4. 如使用本地 WeShop 服务，验证 `WESHOP_LOCAL_SERVICE_URL` 是受信任的本机地址，并按 CLI 实际支持的方法配置它。
5. 启动表单服务后提供健康检查；只有以上条件满足时，页面才启用“提交生成任务”。

## 强制启动与交付

实现完成后，Agent 必须自行在用户本机实际启动服务，而不是只写出 README 启动命令、让用户执行命令或要求用户自行排查。Agent 负责从官方来源安装/升级到最新版 WeShop CLI、安装所需依赖、启动并保留服务进程，直至用户能够访问和使用页面。

启动后必须依次确认：

1. 服务已成功监听一个回环地址。若默认端口被占用、无权限或启动失败，自动探测并依次尝试其他空闲回环端口，直至服务成功启动；每次切换后都重新执行健康检查，并报告最终实际地址。只有没有任何可用端口时才报告启动失败。
2. 健康检查返回 CLI 就绪状态，且不泄露任何秘密。
3. 从用户的浏览器或可访问性检查确认 `http://127.0.0.1:<实际端口>` 可打开；出现 `ERR_CONNECTION_REFUSED` 表示服务未交付完成。
4. 页面不是静态 JSON 预览，并且“提交生成任务”按钮在配置就绪时可用。

### 不可跳过的端口存活检查

端口检查是交付门槛，不是 Agent 可自由选择的建议。每次启动、重启、切换端口，以及每次向用户报告服务地址前，必须按顺序完成以下全部检查：

1. 以系统级监听检查确认目标为回环地址上的 `LISTEN` 状态（例如 `lsof`、`ss` 或等价工具）；仅有 PID 文件、终端历史、启动日志或“进程曾创建过”均不通过。
2. 对最终地址执行真实 HTTP `GET /api/health`，要求在短超时内得到 HTTP 2xx 和预期的非秘密就绪字段。
3. 对最终地址执行真实 HTTP `GET /`，要求在短超时内得到 HTTP 200，且响应为页面而非连接错误、重定向占位或静态 JSON。
4. 检查服务进程仍存活且仍保持监听，再报告 URL。若任何检查失败、端口无人监听或收到 `ERR_CONNECTION_REFUSED`，必须视为未交付：重新以可持续方式启动服务，选择一个可用回环端口后从第 1 步重新检查；不得只让用户刷新、不得把旧 URL 当作可用、不得声称已完成。

上述检查的实际端口、监听证据、健康检查 HTTP 状态和页面 HTTP 状态必须记录在最终交付中（不得含 API Key）。

最终交付必须包含：正在运行的本地服务、Agent 已打开或可直接打开的本地 URL，以及已验证的健康检查结果。若端口不可用，Agent 必须先自动更换端口并继续。若当前执行环境缺少运行、监听端口或安装依赖的权限，Agent 必须请求所需权限并在获准后自行完成；不得把命令、README 或手动启动步骤交给用户作为最终交付。

## CLI 驱动的动态表单

用户会提供模型/Agent 意图及需要的参数项，例如：“使用 qwen image edit 模型，参数包括提示词、生成张数和图片”。用户不需要知道 CLI 参数名。

服务必须在用户选择模型后，从当前安装的 WeShop CLI 获取真实契约：

1. 从 CLI 的 Agent 列表、总帮助或等价能力查询中匹配用户说法，确认对应的实际 Agent/命令和版本。（不要透出其他的Agent）
2. 读取该 Agent 的 `--help` 或 CLI 提供的 schema/describe 输出。
3. 提取真实字段：参数名、类型、必填性、枚举、默认值、数值范围、重复值规则，以及文件或 URL 的媒体输入要求。
4. 动态生成表单。表单可显示英文名，但提交时必须使用 CLI 实际支持的参数名。
5. 用户未提及但 CLI 必需的字段，必须显示并要求用户填写；CLI 未声明的字段不得展示为可提交参数。

例如：只有当当前 CLI 明确公开 `--batch` 时，才能展示“生成张数”并提交 `--batch`；只有当 CLI 明确要求图片时，才能按其要求提供文件选择或 URL 输入。不得根据截图、历史表单或常识猜测字段。

### 固定运行时字段

以下字段由本地表单服务管理，不由 CLI 参数发现推导，发起CLI请求时需要把下面两个参数带上`--safeGenerate='off' ` 和`--resultBase64=false` 

- `safeGenerate`：表单必须提供 `off` / `on` 选项。仅当本地服务/CLI 适配层明确支持时才传递；否则保留在本地请求元数据中并说明未传给 Agent。
- `resultBase64`：控制服务偏好的返回格式，不作为 Agent CLI 参数；无论该偏好值如何，服务都必须兼容 CLI 实际返回的 URL 或 Base64。

除以上字段外，所有 Agent 可编辑参数必须来自该次 CLI 的已验证输出。

## 本地服务接口职责

接口路径和技术栈可由实现选择，但服务必须提供等价能力：

| 能力 | 服务行为 |
| --- | --- |
| 健康检查 | 返回 CLI 就绪状态、版本及不含秘密的故障原因。 |
| Agent 发现 | 返回当前 CLI 可用的 Agent/模型候选项。 |
| 参数 Schema | 给定 Agent/模型后，从 CLI 返回可生成表单的字段定义。 |
| 同步提交任务 | 校验表单数据，安全调用 CLI，并在请求内等待最终结果。记录返回的executionId |
| 页面 UI | 渲染动态表单、执行中状态、任务错误和可访问的成功媒体。 |
| 查询任务 | 根据executionId通过查询获取本次执行的状态。 |
| 上传图片 | 根据本地上传图片获取URL |

提交接口只能接受当前 Schema 允许的字段。要防止 shell 注入：以结构化参数数组调用 CLI，不把用户文本、URL 或 JSON 直接拼入 shell 字符串。

## 同步任务执行和结果展示

1. 服务端再次校验提交值与当前 CLI Schema 一致。
2. 如果该Agent支持图片输入，则需要提供上传图片入口，可根据CLI中上传接口获取URL，在提交是传入。
3. 以 `WESHOP_API_KEY` 环境变量运行 CLI；不得将其作为 `--api-key`、`--apiKey` 或任何普通命令参数传入。
4. 如果同步提交任务后超过5分钟未返回最终结果，可中断。通过记录下来的executionId通过查询接口获取当前任务的状态。如果仍然是进行中的状态则需要每隔2s轮训等待获取结果。
5. 使用 CLI 真实支持的本地服务配置、Agent、媒体输入和参数执行任务，并同步等待 CLI 退出和返回最终结果。
6. 解析 CLI 输出，页面展示最终状态、脱敏错误和逐个媒体结果。每个成功媒体必须同时兼容以下返回形式：
   - URL：校验 URL 非空后直接渲染图片/视频预览，并提供可打开的链接。
   - Base64：识别或从返回元数据取得 MIME 类型，将数据转换为浏览器可渲染的 data URL 后预览；不得把原始 Base64 长文本作为唯一结果展示。
7. 当同一结果同时包含 URL 与 Base64 时，优先使用 URL 展示，并保留 Base64 作为回退；仅存在其中一种时，必须正常展示该种形式。
8. 展示结果，要根据CLI实际返回的内容做展示，可能是Base64也可能是URL。这里要兼容这两种情况，将最终结果展示出来。
9. 只有 CLI 已返回终态成功，且每个预期媒体均成功并具有非空 URL 或有效 Base64 内容时，才能显示任务成功。

若 CLI 进程超时、被取消或异常退出，返回对应状态和脱敏错误；禁止自动重复提交，以免重复生成和计费。

## 页面状态

| 状态 | 页面行为 |
| --- | --- |
| `initializing` | 显示正在检查 CLI 与本地配置；不可提交。 |
| `ready` | 已获取 Agent Schema；可提交。 |
| `validation_error` | 高亮字段错误；不执行 CLI。 |
| `submitting` / `running` | 显示正在等待 CLI 同步返回；避免重复点击。 |
| `success` | 展示全部成功媒体结果，兼容 URL 与 Base64 两种形式。 |
| `partial_success` | 展示成功媒体（URL 或 Base64）及失败项目。 |
| `failed` / `timeout` | 显示脱敏错误和安全的下一步提示。 |

## 验证与交付

在报告完成前，验证以下可观察结果：

1. 服务仅监听本机地址，且浏览器源码、网络请求和服务日志均不含 API Key。
2. 服务进程正在运行，实际本地 URL 可打开，健康检查成功；不能以 README 或未启动的项目文件代替。
   - 必须同时满足“不可跳过的端口存活检查”中的四项证据；PID、日志或后台命令成功本身不构成验证。
3. 页面显示的是从当前 CLI 获取的 Agent 字段，而不是写死的 `z-image` 或历史 JSON。
4. 表单按钮会调用本地服务的同步提交接口，而不是仅复制 JSON。
5. 测试的时候不要通过CLI去实际生成。
6. 使用一个已支持的 Agent 完成从填写、同步执行到媒体结果显示的完整闭环。
7. 检查每个媒体结果的终态成功和非空 URL 或有效 Base64 内容；不能仅凭“CLI 已启动”宣称任务完成。
8. 分别验证一个 URL 返回和一个 Base64 返回能够在页面中预览；不得只显示原始 Base64 文本或只支持其中一种格式。

当 CLI 未提供用户指定模型或参数时，服务必须清楚说明当前 CLI 的支持情况并阻止提交；不得编造字段、静默删除参数或降级为静态预览。
